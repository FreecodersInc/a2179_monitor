# Гипотезы (бэклог)

Черновик для обсуждения. Каждая гипотеза проверяемая и опровержимая: заранее записано, какое число её опровергает, какой метрикой меряем и какие данные нужны. Когда берём гипотезу в работу, заводим `EXP-NNN` по [`TEMPLATE.md`](TEMPLATE.md) и ставим ссылку сюда. Решения по итогам идут в ADR.

Общая постановка: есть **цель** (профиль в `targets/`, ADR-0010) и поток объявлений или документов. Задача отличить «это именно тот товар» от «про то же самое» (тот же бренд, модель, тема, но другая деталь, аксессуар, услуга, спрос вместо предложения). A2179 экран первый полигон, гипотезы сформулированы для любой цели.

Основная метрика, если не сказано иное: **P при R = 1.0** (precision при полном recall, порог подбирается по набору, плюс 5-fold), потому что пропуск нужного хуже лишнего уведомления (ADR-0002). Вторичные: F1, FP на 100 негативов, P/R только на реальных строках.

| id | гипотеза | опровергается, если | метрика | данные | статус | связи |
|---|---|---|---|---|---|---|
| H-01 | Bi-encoder (косинус к прототипам) меряет тему, а не товар: на трудных негативах (та же модель, другая деталь или услуга) чистый dense не выходит выше P 0.70 при R 1.0, ни на какой цели и ни на какой из 3 моделей | хоть одна модель на хоть одной цели даёт P ≥ 0.85 при R 1.0 (5-fold) | P@R1, 5-fold | 2 цели, ≥200 реальных строк на цель, ≥30% трудных негативов | частично (EXP-001: MiniLM P 0.600 на 99 строках) | EXP-001, EXP-002, ADR-0007 |
| H-02 | Профиль из явных правил (модель + тип детали + исключения) переносится на новую цель дёшево: за ≤ 2 часа работы hybrid regex + TF-IDF даёт P ≥ 0.95 при R 1.0 | P < 0.90 при R 1.0 или профиль потребовал > 4 часов | P@R1, время на профиль | вторая цель (`targets/<new>.json`) и ≥200 размеченных строк | planned | ADR-0010, M-001 |
| H-03 | Пороги похожести не переносятся между целями: TF-IDF пороги A2179 на новой цели теряют ≥ 5 п.п. recall, поэтому пороги должны жить в профиле | recall на новой цели с порогами A2179 падает < 2 п.п. | ΔR при фиксированных порогах | как H-02 | planned | ADR-0010, ADR-0007 |
| H-04 | Cross-encoder или NLI вопрос «продаётся ли здесь X» на top-k после bi-encoder поднимает dense P при R 1.0 минимум на 0.15 | прирост < 0.05 | P@R1, latency на объявление | как H-01, GPU раннер | planned | H-01, ADR-0008 |
| H-05 | Намерение (продаю / ищу / сервис) правилами определяется с точностью ≥ 0.95, а dense без правил путает «kupujem / trazim» с продажей в ≥ 10% случаев | правила < 0.90 или dense ошибается < 3% | accuracy по намерению, FP от «ищу» | ревью кандидатов `eval/enrich.py` с полем intent, ≥ 50 строк «ищу» | planned | EXP-002 |
| H-06 | Прототипов достаточно ~15 на сторону: удвоение числа прототипов меняет F1 TF-IDF канала < 0.01, половина роняет > 0.03 | удвоение даёт ≥ 0.02 F1 | F1, P@R1 по числу прототипов (кривая) | текущий набор, позже EXP-002 | planned | EXP-001 |
| H-07 | Сама разметка однозначна: два независимых ревьюера согласны с κ ≥ 0.8 на «это цель». Иначе потолок метрик задаёт определение задачи, а не модель | κ < 0.6 | Cohen κ, список спорных kind | 100 строк, размеченных двумя людьми вслепую | planned | EXP-002 |
| H-08 | Синтетика завышает: на синтетических строках P при R 1.0 выше, чем на реальных, на ≥ 0.05 у каждого канала | разница < 0.02 у всех каналов | P@R1 real only против synthetic only | EXP-002 (реальных строк ≥ синтетических) | частично (EXP-001 считает real only) | EXP-001, EXP-002 |
| H-09 | Цена как признак: полоса цены цели (аксессуары дешёвые, целые ноутбуки дорогие) снимает ≥ 30% FP без потери recall | FP падает < 10% или recall теряется | FP при R 1.0, ΔR | строки с ценой (≥ 150), полоса из профиля | planned | ADR-0006, ADR-0010 |
| H-10 | Нормализация письменности (латиница, кириллица, русский в одно) даёт TF-IDF ≥ 5 п.п. recall на строках sr_cyr и ru при том же P | без нормализации recall на них падает < 2 п.п. | R по языкам при фиксированном P (ablation) | текущий набор по `lang`, больше кириллицы из EXP-002 | planned | ADR-0002 |
| H-11 | Инженерия: CUDA и CPU дают одни и те же оценки эмбеддера (max ∣Δcos∣ < 1e-4), так что пороги не зависят от устройства | ∣Δcos∣ ≥ 1e-3 хоть на одной строке | max ∣Δcos∣ по набору | раннер с CUDA, тот же набор, два прогона | planned | EXP-000, ADR-0005, ADR-0008 |

## Как берём в работу
1. Выбрали гипотезу, завели `experiments/EXP-NNN_<slug>.md`, скопировали сюда гипотезу и критерий опровержения дословно (до прогона).
2. Данные: версия набора (blob, sha256) в записи. Нужен новый набор, сначала задача в `work/`.
3. Прогон через CI на раннере, числа берём из `results/<base>.json`.
4. Статус здесь: `running` → `supported` / `refuted` / `inconclusive`, со ссылкой на EXP.
