# ADR-0012: прозрачный гибридный поиск без векторной БД

## Контекст и проблема
Нужно отличать «именно тот товар» от «того же по теме» в потоке из сотен объявлений в день. Объём маленький, важна объяснимость каждого решения (почему пришло уведомление), а dense модель одна путает тему с товаром (EXP-001, EXP-002). Вопрос: на чём строим исследовательский стек ретрива и в какой форме сравниваем варианты.

## Факторы решения
* объём: сотни объявлений, десятки прототипов, полный перебор дешевле любой индексации
* каждое число и каждое решение должно объясняться (какой канал, какой вес, какой порог)
* варианты должны сравниваться на одном наборе одной таблицей
* без новой инфраструктуры (сервисы, БД)

## Рассмотренные варианты
* векторная БД (ANN индекс) и retrieval по ней
* один канал (только TF-IDF или только MiniLM) с порогом
* несколько прозрачных каналов, явное слияние с весом, правила отдельным членом

## Решение
Третий вариант, как он реализован в `eval/sweep.py`:
* каналы: TF-IDF char 3..5 (как в мониторе), BM25 по словам (k1 1.5, b 0.75, IDF по прототипам), косинус MiniLM к прототипам. Каждый даёт sim_pos, sim_neg (макс. похожесть на позитивные и негативные прототипы цели) и скаляр d = sim_pos − sim_neg
* перед слиянием каждый скаляр min-max нормализуется по набору
* слияние: convex combination w·a + (1 − w)·b, w по сетке 0.0…1.0 шаг 0.1, порог подбирается на каждом w. RRF (k 60) считается рядом как контроль, не как основной метод
* явные признаки цели (+1 нужная деталь, −1 за каждую группу «другая деталь, аксессуар, сервис, ищу») отдельным членом: (1 − lam)·base + lam·feat, lam по той же сетке, вес виден в таблице
* model gate из правил профиля стоит перед каждым каналом, hybrid = regex OR (gate AND score ≥ t) (ADR-0002)
* никакой векторной БД: всё считается полным перебором, dense оценки кэшируются файлом `dense_scores.jsonl`

Монитор при этом работает на регулярках + TF-IDF (ADR-0007), остальные каналы пока только в исследовании, пока eval не покажет выигрыш (ADR-0013).

### Последствия
* Хорошо: каждая строка таблицы воспроизводима и объяснима, веса видны, лучший вариант на 430 строках (tfidf+feat lam 0.4, P 0.857 при R 1.0, 8 FP) это формула в одну строку.
* Хорошо: новый канал (E5, cross-encoder) добавляется как ещё один скаляр в ту же таблицу.
* Плохо: полный перебор не масштабируется на миллионы документов, тогда понадобится индекс (новый ADR).
* Плохо: min-max нормализация по набору зависит от набора, пороги между версиями набора могут сдвигаться (H-21).

### Как проверяем
`eval/sweep.py` и `eval/plots.py` в каждом прогоне CI, числа в `results/`. Сравнение CC против RRF и роль lam это гипотезы H-14, H-15, H-26.
