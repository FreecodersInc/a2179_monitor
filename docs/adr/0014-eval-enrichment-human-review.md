# ADR-0014: набор eval растёт через eval/enrich.py, каждую авто метку смотрит человек

## Контекст и проблема
99 строк, из них 59 синтетических, слишком льстили моделям. Нужны сотни реальных объявлений с трудными негативами, но размечать с нуля дорого, а метки модели тянут набор к самой модели.

## Факторы решения
* реальные объявления с площадок, где работает монитор
* разметка быстрая, но решение за человеком
* авто метки прозрачные (видно почему), без LLM
* набор только растёт, история в git

## Рассмотренные варианты
* разметка руками с нуля
* авто метки моделью матчера без ревью
* авто метки правилами с причиной, обязательное ревью, merge только просмотренных

## Решение
Третий вариант, `eval/enrich.py`:
* `collect` собирает кандидатов машинерией монитора (общий лимитер, пагинация), выкидывает дубли набора
* предметка только правилами: regex профиля, группы признаков, намерение (продаю, ищу, сервис), оценка матчера, у каждой строки `reason`, `flags`, `needs_review: true`, `reviewed: false`
* порядок для ревью: сначала расхождения правил и матчера, потом трудные негативы, потом позитивы
* человек ставит `reviewed`, правит `label` и `kind`, спорные помечает `review_unsure`
* `merge` добавляет только `reviewed` строки, `source: real`, новые id, ничего не удаляет
* версия набора фиксируется в EXP записи (git blob, sha256)

### Последствия
* Хорошо: 331 реальная строка за один круг (3b678fa), три метки поправлены руками, спорные видны.
* Плохо: один разметчик, согласие не измерено (H-07), авто метка может подталкивать ревьюера.
* Плохо: запросы сбора задают, какие объявления вообще попадут в набор.

### Как проверяем
`tests/test_enrich.py` (офлайн), EXP-002. Согласие разметчиков H-07, LLM разметчик H-22, active learning H-29.
