# ADR-0019: в CI по умолчанию только кэшированные малые эмбеддеры

## Контекст и проблема
Реестр моделей для свипа включает и тяжёлые (bge-m3, e5-large, e5-large-instruct, LaBSE). Даже на CPU (ADR-0018) они долго считаются и много едят память. Обычный прогон на каждый push не должен сам поднимать большие модели.

## Факторы решения
* дефолтный CI должен быть предсказуемым по времени и памяти
* малые модели из кэша (до 300M параметров) достаточны для повседневного сравнения
* большие модели остаются доступны, но только по явному списку
* CI ничего не докачивает без отдельного разрешения

## Рассмотренные варианты
* `A2179_CI_EMBEDDERS=cached`: всё, что уже лежит в кэше, включая большие
* `all`: полный реестр на каждый push
* `cached-small` по умолчанию (модели из кэша до 300M параметров), большие только если назвать их явно

## Решение
Третий вариант. По умолчанию `A2179_CI_EMBEDDERS=cached-small`: из кэша берутся модели не тяжелее `A2179_MAX_PARAMS_M=300` (minilm, mpnet, e5-small, e5-base и варианты, bge-base-en, e5-base-en). bge-m3, e5-large, e5-large-instruct и LaBSE считаются, только если их перечислить, например `A2179_CI_EMBEDDERS=cached-small,bge-m3,e5-large,e5-large-instruct,labse`. Группы и имена можно смешивать.

### Последствия
* Хорошо: обычный push не запускает тяжёлые модели и не раздувает прогон.
* Хорошо: большой свип остаётся одной переменной, без правки кода.
* Плохо: числа по bge-m3 и large не появляются сами, их надо запросить. Для T-008 это ожидаемо: сначала честная проверка на свежих лотах (ADR-0021).

### Как проверяем
Прогон с дефолтом не берёт bge-m3, e5-large, e5-large-instruct и LaBSE. Явный список этих имён их включает. Покрытие в тестах свипа и в [docs/ci.md](../ci.md).
