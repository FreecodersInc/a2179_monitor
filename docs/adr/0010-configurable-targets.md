# ADR-0010: цель поиска как профиль в targets/, не в коде

## Контекст и проблема
Всё специфичное для одного случая (MacBook Air A2179, экран, Сербия) было зашито в код: модели и исключения в `a2179/rules.py`, прототипы в `a2179/prototypes.py`, источники, цена цели и пороги в `a2179/config.py`, текст про A1932 в `run.py`. Для проверки гипотез (experiments/HYPOTHESES.md) нужно менять цель без правки кода.

## Факторы решения
* поведение для A2179 не меняется ни на одну строку решения
* профиль читается человеком и лежит в git (прозрачность, как ADR-0002)
* новая цель без программирования, ошибки профиля видны сразу
* без новых зависимостей и инфраструктуры

## Рассмотренные варианты
* оставить код, копировать репо под каждую цель
* профиль как Python модуль (гибко, но цель становится кодом)
* профиль как JSON (`targets/<name>.json`): правила (regex и списки слов), прототипы, defaults для конфига
* обучаемый классификатор вместо правил (не прозрачно, нужна разметка до старта)

## Решение
JSON профиль, загрузчик `a2179/target.py`. Секции:
* `rules`: уровни модели (`models`, с необязательным `accept_option` и `alert_note`), `family` и `conflict` (gate для канала похожести), `weak` (наборы шаблонов, все должны найтись, с `unless_conflict`), списки слов `part_terms`, `donor_terms`, `soft_excl_terms` (через `normalize()`), шаблоны `strong_part`, `hard_excl`, `specs`, `no_model_reason`
* `prototypes`: positive и negative для TF-IDF, BM25 и эмбеддера
* `defaults`: всё, что раньше было в `DEFAULTS` для этой цели (`sources`, `target_usd`, `thresholds`, `accept_*`)
* `label` для уведомлений

Порядок конфига: общие defaults ← defaults профиля ← `config.json` ← переменные окружения. Цель выбирает `"target"` в `config.json` (имя из `targets/` или путь к .json) или `A2179_TARGET`. По умолчанию `a2179_screen`.

Логика `classify` осталась той же функцией, только читает правила из профиля. Профиль A2179 сгенерирован из старого кода, тесты сверяют шаблоны и 298 решений (набор, прототипы, сухой прогон, оба значения accept_a1932) со снимком до рефакторинга, плюс eval выдаёт те же TP/FP/FN/TN.

### Последствия
* Хорошо: новая цель = новый JSON и свой размеченный набор, пороги и источники вместе с правилами.
* Хорошо: старые имена (`rules.STRONG_MODEL`, `prototypes.POSITIVE`, `config.DEFAULTS`) остались как вид профиля по умолчанию.
* Плохо: регулярки в JSON читать тяжелее, чем в Python (экранирование). Структура решения (модель → исключения → деталь → донор) общая для всех целей, цель другой формы (например услуга, а не деталь) может потребовать новой секции.
* Не сделано в этом шаге: eval сторона (`eval/enrich.py` запросы, группы признаков `eval/sweep.py`, путь к набору) ещё про A2179, план в `work/M-001`.

### Как проверяем
`tests/test_target.py`: шаблоны и решения A2179 равны снимку, defaults равны старым, игрушечный профиль (iPhone 11 батарея) работает через `config.json` и `A2179_TARGET`, битые профили дают понятную ошибку. Полный набор тестов зелёный, `eval/run_eval.py` даёт те же числа.
